# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a **multi-cluster banking transaction demo platform** designed to demonstrate high availability, elasticity, data consistency, and zero-downtime upgrades across two OpenShift 4.21+ clusters:

- **`onprem`:** Self-managed OCP. Static baseline capacity. Record-of-truth cluster (PostgreSQL primary, Kafka source, RHACM Hub, Argo CD).
- **`cloud`:** Self-managed OCP. Elastic capacity. KEDA-driven autoscaling (1–20 replicas on Kafka consumer lag).

`onprem` and `cloud` are **logical roles, not infrastructure**. Either cluster can run on any provider or on bare metal — AWS, GCP, Azure, vSphere, whatever is available for a given test run. Nothing in the manifests, scripts, or app config is tied to a specific cloud; only the two context names (`onprem`, `cloud`) and their roles (hub/record-of-truth vs. elastic spoke) matter. Do not assume or hardcode a specific cloud provider anywhere in this repo.

Cross-cluster connectivity is provided by **Red Hat Service Interconnect (RHSI)** over mTLS. GitOps is managed by **OpenShift GitOps (Argo CD)** with Kustomize overlays per cluster. Both clusters are managed by **RHACM 2.16+**.

## Architecture

### Application Services (Quarkus 3)

| Service | Role | Notes |
|---|---|---|
| `transaction-generator` | Emits synthetic DEBIT/CREDIT `TransactionEvent`s to Kafka at configurable TPS | JVM mode; ConfigMap-driven TPS |
| `transaction-processor` | Consumes Kafka, validates balance, writes to PostgreSQL, emits `TransactionCommitted`; failed transactions emitted to DLQ | JVM mode + KEDA; cloud instance writes to onprem PostgreSQL via RHSI; `OWNED_PARTITIONS` env var restricts consumption to cluster-specific partitions (onprem: 0-11 · cloud: 12-23) |
| `account-service` | Balance reads via Quarkus `@CacheResult` in-process cache; reads PostgreSQL directly | HPA CPU 60%, 1–20 replicas (both clusters) |
| `ledger-service` | Authoritative running balance; serves REST to dashboard-backend | cloud instance reads from onprem PostgreSQL via RHSI (`postgresql-primary`) |
| `cluster-gateway` | Traffic weight control; aggregated `/health` and `/metrics`; RHSI link break/restore (`LinkResource.java`, cloud only) | Manages Istio VirtualService weights; fabric8 `KubernetesClient` for Deployment reads (both clusters) and `kafka-bootstrap`/`postgresql-primary`/`apicurio-registry` Skupper Listener management (cloud only, see rbac-link.yaml) |
| `dashboard-backend` | Polls both clusters every 500ms, aggregates, streams `MetricsPayload` via WebSocket | Quarkus WebSocket |
| `dashboard-frontend` | Live dashboard: cluster map, TPS gauges, chaos panel, compliance widget | React 18 + Patternfly 5 |

### Infrastructure Components

- **Streams for Apache Kafka (AMQ Streams 3.2 / Kafka 4.2.0):** KRaft mode (ZooKeeper removed). Topology: 3 controller nodes (5Gi PVC each) + 3 broker nodes (20Gi JBOD PVC each), managed via `KafkaNodePool` resources. Topics: `transactions-raw` (24 partitions), `transactions-committed` (3 partitions), `transactions-dlq` (3 partitions). onprem is source; cloud receives via MirrorMaker 2.
- **MirrorMaker 2:** Replicates `transactions-raw` only (DR copy — see Critical Data Flow below) onprem → cloud via a dedicated Skupper tunnel (`kafka-bootstrap-mm2:9094`, separate from the `kafka-bootstrap:9092` tunnel everything else uses — see Phase 1 Operational Notes for why). Uses `IdentityReplicationPolicy` so topic names are not prefixed. Deployed to cloud only.
- **Apicurio Registry 2.5.11.Final (kafkasql):** Avro schema registry on onprem only. Enforces backward compatibility. Requires both `APICURIO_KAFKASQL_BOOTSTRAP_SERVERS` (kafkasql storage) and `KAFKA_BOOTSTRAP_SERVERS` (SmallRye AdminClient health check) env vars.
- **PostgreSQL (Crunchy Postgres for Kubernetes v5):** onprem = 3-node HA primary with PgBouncer. cloud = streaming standby (read-only). **Both clusters use the default storage class** — no storage class names are pinned in manifests.
- **RHSI Router:** onprem issues the link token and exposes `kafka-bootstrap`, `postgresql-primary` as virtual services to cloud.
- **OpenShift Service Mesh 2 (Istio):** mTLS, traffic splitting, circuit breaker per cluster.
- **Custom Metrics Autoscaler (KEDA):** Scales `transaction-processor` on Kafka consumer group lag (threshold: 100 messages). Operator namespace: `openshift-keda`.

### Namespaces

- `banking-demo` — Application workloads (generators, processors, account/ledger services, dashboard).
- `banking-infra` — Infrastructure (Kafka, PostgreSQL, RHSI, Apicurio).
- `open-cluster-management` — RHACM Hub (onprem only).
- `openshift-gitops` — Argo CD (onprem only).
- `istio-system` — OSSM Control Plane (both clusters).
- `openshift-keda` — Custom Metrics Autoscaler (KEDA) ScaledObjects (both clusters).
- `stackrox` — RHACS Central (onprem) + Sensor (cloud).
- `banking-monitoring` — Grafana + Jaeger + Prometheus (onprem); Jaeger + Prometheus federated to onprem via RHACM Observability (cloud).

### Critical Data Flow

1. `transaction-generator` (onprem) → onprem Kafka partitions 0–11; `transaction-generator` (cloud) → cloud Kafka partitions 12–23
2. MirrorMaker 2 replicates `transactions-raw` onprem → cloud (DR copy; cloud processor ignores MM2-replicated partitions 0–11)
3. `transaction-processor` (onprem) consumes partitions 0–11 from onprem Kafka; cloud processor consumes partitions 12–23 from cloud Kafka — **no message is processed by both clusters**
4. Both processors validate balance via `account-service` (Quarkus `@CacheResult` + `@CacheInvalidate` → PostgreSQL, optimistic version locking)
5. **cloud processor writes committed transactions to onprem PostgreSQL primary via RHSI** (tunnelled JDBC)
6. Failed transactions (insufficient funds, version conflict, service error) → `transactions-dlq` (Avro `TransactionFailed`); in-memory counters surfaced via `/api/processor/stats`
7. `ledger-service` consumes `TransactionCommitted` and updates running balance
8. `dashboard-backend` polls both ledger services + processor stats every 1 s → WebSocket push to frontend

### Chaos Scenario: RHSI Link Partition

When onprem's banking-infra services become unreachable from cloud (delete the **`kafka-bootstrap`**, **`postgresql-primary`**, and **`apicurio-registry`** Skupper `Listener` CRs in `banking-infra` on cloud — **not the `Link` CR or any Secret**, see critical note below):
- cloud processor's DB/Apicurio health checks go DOWN with real `Connection refused`/`connection attempt failed` errors; affected transactions are rejected to the DLQ
- onprem continues processing 100% of committed transactions unaffected
- On recovery (re-apply the Listeners): cloud processor reconnects and commits backlog
- **MM2 is unaffected and keeps mirroring `transactions-raw` throughout** — it runs over its own dedicated `kafka-bootstrap-mm2:9094` tunnel (see "MirrorMaker 2 needs its own dedicated listener/tunnel" in Phase 1 Operational Notes), which this toggle intentionally does not touch. This changed as of the 2026-09-04 advertised-listener fix — previously (when MM2 shared the `kafka-bootstrap` tunnel with everything else, back when MM2 was still `replicas: 0` and this had never been exercised) breaking the link would have paused it too.

The dashboard's "Traffic & Chaos" page exercises this for real via `LinkFailurePanel.tsx` → `PUT /api/backend/link/break|restore` (dashboard-backend) → `PUT /api/gateway/link/break|restore` (cloud `cluster-gateway`, `LinkResource.java`, fabric8 `KubernetesClient` + `GenericKubernetesResource` for the `skupper.io/v2alpha1` `Listener` CRD). Break deletes all three Listeners; restore recreates any missing one from a spec that mirrors `infra/skupper/cloud/listeners.yaml` verbatim — the spec is fully static (no secret material, no per-run randomness), so **no in-memory caching and no cache-loss/409 path is needed at all**. RBAC (`get`/`delete` on the three named `listeners.skupper.io` resources, `create` on the resource type, namespace `banking-infra`) is added only in `app-services/cluster-gateway/overlays/cloud/rbac-link.yaml` — onprem never gets it, since these Listeners only exist on cloud.

**CRITICAL — confirmed live: this mechanism deliberately does NOT touch the `Link` CR, because the dashboard's own control-plane channel to cloud depends on a *separate* Listener/Connector pair.** `dashboard-backend` runs on **onprem only** and reaches cloud's `cluster-gateway`/`ledger-service` exclusively through their own Skupper Listener (onprem, routing keys `cloud-cluster-gateway`/`cloud-ledger-service`) / Connector (cloud) pair — confirmed live via `oc get listeners,connectors -n banking-infra` on both clusters; cloud exposes no public Route for this (or anything else — see "No routes on cloud cluster" below), so this tunnel is the *only* path. An earlier version of this feature deleted the whole `Link` CR to sever the tunnel (see history below) — that genuinely broke Kafka/Postgres/Apicurio access, but it also killed the `cluster-gateway`/`ledger-service` channel the dashboard's *own* "restore" button needs, so restore could never succeed from the UI once a real break occurred — a network partition can't heal itself by sending a command through the partition. Deleting only the three banking-infra Listeners leaves the Link and the `cluster-gateway`/`ledger-service` Listener/Connector pair completely untouched (confirmed live: `Link` stays `Ready`, `SITES IN NETWORK` stays 2, and onprem's `dashboard-backend` can still reach cloud's `/api/gateway/health` throughout the outage) while still producing the full documented effect (confirmed live: `rejectedTotal` climbed by 51 "service error" rejections during a real test window, processor health flipped DOWN then back UP cleanly on restore).

**Iteration history (both superseded, kept for context):** (1) The very first implementation deleted only the `skupper-link` Secret — that name doesn't exist anywhere in the cluster; the real object is `onprem-link-token` (`bootstrap-phase1.sh` Step 6, a fixed literal, not environment-generated). (2) After correcting the name, deleting only the `onprem-link-token` Secret still had **zero observable effect** — confirmed live via `skstat -c` on the cloud `skupper-router`, which showed the `inter-router` connection still fully alive (TLSv1.3, x.509, unaffected uptime) minutes after the Secret was gone, because Skupper's router authenticates once at connection time using already-loaded cert material and never re-checks the Secret. Deleting the `Link` CR *did* sever the connection for real (confirmed: `SITES IN NETWORK` 2 → 1), which is how (1)/(2)'s ineffectiveness was diagnosed — but as explained above, that approach was itself replaced by the Listener-only mechanism once its restore-unreachability problem was found.

**What to actually expect on cloud during "Interconnect Broken" — confirmed live, seven findings:**

1. **Postgres read AND write both go DOWN together on cloud — by design, not a bug.** `account-service`/`ledger-service`'s `"read"` datasource is meant to hit a local cloud PostgreSQL standby (`postgres-ha`), but standby replication was never actually configured in this environment (needs a shared S3/GCS pgBackRest repo — see the PGO standby notes in Phase 2 below). `DATASOURCE_READ_URL` is therefore unset and `"read"` silently falls back to `${DATASOURCE_URL}` — the *same* RHSI-tunneled `postgresql-primary` connection as the default datasource. Until real standby mode is enabled, both go down together; this accurately reflects the current deployment, it isn't something the chaos feature broke.

2. **`transaction-generator` looked like "Kafka is inaccessible" but the broker was fine — the real blocker was Apicurio, and the fix needed two parts, not one.** `KAFKA_BOOTSTRAP_SERVERS` correctly points at the local cloud Kafka broker, unaffected by the Listener break. First cause found: `apicurio.registry.find-latest=true` on the generator's outgoing channel (the only place in the codebase this was set) forced an Apicurio round-trip on *every* send instead of caching after the first — removed, since this demo uses one fixed schema per topic for its whole life and nothing about which schema is used changes.

   **That alone wasn't sufficient — confirmed live**: `SRMSG00034: Insufficient downstream requests to emit item` still recurred after a later RHSI outage even with `find-latest` already removed, and kept recurring for *minutes after the link was restored* — proving it wasn't a live-network symptom at that point (also independently confirmed: zero `SRMSG00034` occurrences over 3 minutes of steady load with no chaos interference at all, ruling out a plain capacity/config mismatch). Real root cause: Apicurio's serde base config (`io.apicurio.registry.serde.SerdeConfig.CHECK_PERIOD_MS`, property `apicurio.registry.check-period-ms`) independently re-validates a channel's cached schema mapping every **30s by default**, regardless of `find-latest` — this applies to the shared serializer/deserializer base class, so it's universal to every Avro channel in the system, not generator-specific. Confirmed by decompiling the actual Apicurio Vert.x REST client (`apicurio-common-rest-client-vertx-0.1.18.Final`, `VertxHttpClient.createClientOptions`): it exposes **no** connect/read/idle timeout option in this library version — only TLS settings — so that periodic check hangs for Vert.x's ~60s default connect timeout when Apicurio is unreachable, and the reactive Kafka sink never gets a completion callback for whatever record was in flight when it fired — **permanently leaking one demand credit per occurrence**. Enough leaked credits over enough 30s cycles during an outage exhausts `max-in-flight` for good; unlike a live network issue this does **not** self-heal once Apicurio comes back, since the credits are already gone — only a pod restart clears it. Fixed by raising `check-period-ms` to effectively "never" (24h) on every Apicurio channel across `transaction-generator`, `transaction-processor`, and `ledger-service`. Also added a defensive `emitter.hasRequests()` check in `TransactionGeneratorService.generateBatch()` (MicroProfile's own documented usage pattern) so any future demand exhaustion, from any cause, skips a synthetic transaction instead of throwing and spamming ERROR-level stack traces. **Residual limitation, accepted, not fixed**: a genuinely cold start (no prior successful resolution at all) during an active outage still hangs on the very first send/consume — there's no timeout knob available in this client to bound that.

   **Fully re-verified after the `check-period-ms` fix, live, with a genuinely sustained outage**: broke the link for real, held it broken for a full 4 minutes under steady generated traffic (not a quick blip), then restored — zero `SRMSG00034` occurrences throughout, zero pod restarts across all 8 cloud pods (`account-service`, `ledger-service`, 7× HPA-scaled `transaction-processor`), and real traffic (`totalLedgerEntries`) climbing again within seconds of restore.

3. **Pods were restarting during the outage — a second, distinct root cause: SmallRye Reactive Messaging wires Kafka channel health into `@Liveness`, not just `@Readiness`.** Confirmed live: `ledger-service`/`transaction-processor` (both consume/produce Kafka) racked up real restarts during a chaos test; `account-service` (pure REST+DB, no Kafka) had zero. Events showed `/health/live` itself returning 503 and `"...failed liveness probe, will be restarted"`. Root cause, confirmed by decompiling the actual classes in use: `quarkus-messaging` pulls in `smallrye-reactive-messaging-health`, which registers `SmallRyeReactiveMessagingLivenessCheck` (`@Liveness`) *and* `SmallRyeReactiveMessagingReadinessCheck` (`@Readiness`), both backed by the same `HealthCenter` aggregating per-channel `KafkaSourceHealth`/`KafkaSinkHealth`. So a degraded channel (e.g. the Avro deserializer hung on unreachable Apicurio, per finding 2) fails liveness and gets an otherwise-perfectly-healthy pod killed — restarting doesn't fix a downstream outage, Kafka clients reconnect on their own once it's back (and the JDBC fix below already makes Agroal self-heal without a restart too). The registration is gated by a **single combined build-time toggle**, confirmed via `ReactiveMessagingBuildTimeConfig` (`@ConfigRoot(name="messaging")`, field `healthEnabled` → `@ConfigItem(name="health.enabled")`) — i.e. `quarkus.messaging.health.enabled`, no separate liveness-only switch exists. Set to `false` in `transaction-processor`/`ledger-service`; readiness for DB-down is still correctly covered by Quarkus's own built-in `DataSourceHealthCheck` (confirmed `@Readiness`-only, unaffected by this toggle). `account-service` has no Kafka channels so this never applied to it — confirmed by its zero restarts in the same window.

4. **`DatabaseConnectivityMonitor`** (`account-service`, `ledger-service`, `transaction-processor` — same class name/log format in all three) gives consistent, low-noise, transition-only DB connectivity logging: `@Startup`-registered background poller (same `ScheduledExecutorService` convention as `KafkaPartitionStats`), checks each configured datasource's `Connection.isValid(2)` every 5s, and logs exactly once on each transition (`"Database connectivity LOST (datasource=...): <cause>"` / `"...RESTORED (datasource=...) after Ns"`) instead of SmallRye Health's own noisy every-probe `SRHCK01001` line. Purely additive — doesn't touch liveness or readiness. Re-verified live across all 7 HPA-scaled `transaction-processor` pods simultaneously during a real sustained outage: every pod logged exactly one `LOST` and exactly one `RESTORED (after ~271-276s)`, no repeats.

5. **`bootstrap-phase2.sh` warned about a missing `kubectl.kubernetes.io/last-applied-configuration` annotation on the three Listeners after any dashboard-triggered restore.** `LinkResource.java`'s restore path recreates them via fabric8's plain `create()`, which never sets that annotation — unlike `oc apply` (which sets it so future applies can compute a 3-way-merge diff). Harmless (`oc apply` patches it in and proceeds — `... configured`, not an error) but noisy on every subsequent `oc apply -f infra/skupper/cloud/listeners.yaml` (including inside `bootstrap-phase2.sh` Step 3) after a UI restore. Fixed by having `buildListener()` set the annotation itself with content matching exactly what `oc apply` would produce — confirmed live: re-running the same `oc apply` command twice after a UI-triggered restore now reports clean `unchanged` with zero warnings, same as the objects that were never touched by the chaos feature.

6. **Disabling messaging liveness (finding 3) traded a restart-storm bug for a silent-starvation bug — a single deserialization failure permanently kills the Kafka consumer with nothing left to notice.** Confirmed live (2026-09-04): a transient `apicurio-registry...: Name or service not known` DNS blip through RHSI made a value deserialization fail on `transactions-in`/`committed-in`. Without a `DeserializationFailureHandler` configured, SmallRye's `DeserializerWrapper` (confirmed by decompiling `smallrye-reactive-messaging-kafka-4.19.0`) treats *any* unhandled deserialization exception as fatal: it logs `SRMSG18249` ("configure a DeserializationFailureHandler to recover from errors"), the consumer executes `SRMSG18224` ("consumer revoked re-balance listener"), and never rejoins the group — permanently, for the life of the pod. Because finding 3 disabled `quarkus.messaging.health.enabled` precisely to stop restarts on transient degradation, nothing detected this: all 6 `transaction-processor` pods and `ledger-service` on cloud sat `1/1 Ready` (DB-only readiness) with **zero active consumers** for ~40 minutes, backing `transactions-raw` up by ~17k messages per owned partition, until manually restarted. This is a fundamentally different failure shape than finding 3's connection-level degradation (which the Kafka client really does retry/reconnect on its own) — a deserialization exception is not retried by the connector at all without an explicit handler.

   Fixed with a `DeserializationFailureHandler<Object>` bean (`RetryingAvroDeserializationFailureHandler`, registered per channel via `mp.messaging.incoming.<channel>.value-deserialization-failure-handler=retrying-avro-deserializer`, confirmed via `KafkaConnectorIncomingConfiguration.getValueDeserializationFailureHandler()`) in both `transaction-processor` and `ledger-service`. It overrides `decorateDeserialization` to retry the failing deserialization — which re-attempts the same Apicurio schema lookup, cached after the first success per `check-period-ms` from finding 2, so only the first record hitting a cold/uncached schema mapping ever pays this cost — with Mutiny backoff (1s → 15s) for up to a 4-minute budget (matching the sustained-outage duration already re-verified in finding 2) before giving up. Mirrors the JDBC `socketTimeout`/`connectTimeout` fix below: self-heal within the same attempt instead of needing a restart. Only if the budget is exhausted does it mark a new, narrow `@Liveness` bean (`KafkaConsumerLivenessCheck`, backed by `KafkaConsumerHealthState`) DOWN and re-throw — deliberately separate from finding 3's disabled SmallRye messaging health, so only a *confirmed permanent* fail-stop triggers a restart, not ordinary transient degradation. No data loss in either path: the failing record's offset is never committed (`@Acknowledgment(Acknowledgment.Strategy.MANUAL)`), so it's redelivered whether recovery happens via retry or via the resulting pod restart. Confirmed live: consumer group lag drained to 0 and `kafka-consumer-channel` reports `UP` on `/health/live` after redeploy. `bootstrap-phase2.sh`'s Phase 2 checkpoint checks `kafka-consumer-channel` is `UP` on both `transaction-processor` and `ledger-service`, on both clusters — verifying the fix (not just a Running pod) lands on a fresh install too.

   **Operational gotcha hit while deploying this fix**: the Tekton `build-banking-image` pipeline's `git-clone` task clones from the `origin` GitHub remote at a fixed revision (default `main`) — it does **not** see local uncommitted changes. Triggering a `PipelineRun` against uncommitted code silently rebuilds the *previous* committed state with no error. Always `git commit` + `git push origin main` before triggering a rebuild for a code change (manifest-only changes deployed via Argo CD don't need this). Also, since `imagePullPolicy: Always` is paired with a static `:latest` tag (not a resolved digest) in every service's `base/deployment.yaml`, Argo CD sees no manifest diff after a rebuild and does **not** roll out the new image on its own — an explicit `oc rollout restart` on both clusters is still required after every Tekton build to actually pick up the freshly pushed `:latest` image.

7. **Finding 6's fix only covered deserialization failures — an uncaught DB exception thrown from inside the `@Incoming` method body itself hit the exact same fatal fail-stop path, and `ledger-service` (single pod, no HPA) went fully dark with no self-recovery.** Confirmed live (2026-09-04): `TransactionProcessor.process()`'s idempotency pre-check and commit `INSERT`, and `LedgerUpdater.onCommitted()`'s ledger persist, all ran unguarded `QuarkusTransaction.requiringNew().call(...)` calls directly inside the `@Incoming` handler body, with no try/catch. During an interconnect break/restore cycle, the transient JDBC "connection has been closed" window (the same window the `socketTimeout`/`connectTimeout` fix below normally self-heals within seconds) was occasionally enough to throw before Agroal's fast validation kicked in, and that exception propagated straight out of the handler uncaught — hitting SmallRye's *default* `failure-strategy=fail` (`KafkaFailStop`, confirmed by decompiling `smallrye-reactive-messaging-kafka-4.19.0`: its `handle()` reports `fatal=true`), which tears down the Kafka consumer subscription exactly like finding 6's deserialization case, but via a completely different trigger (a business/DB exception, not deserialization) that finding 6's fix does not cover at all. Confirmed via `jcmd 1 Thread.print`: `smallrye-kafka-consumer-thread-0` was entirely absent from the JVM's thread list, not merely idle. Because `quarkus.messaging.health.enabled=false` (finding 3) and `KafkaConsumerLivenessCheck` only watches for *exhausted deserialization retries* (finding 6), nothing detected this — affected pods stayed `1/1 Ready` indefinitely. `ledger-service` runs a single pod with no HPA, so this was a total outage of all cloud ledger updates: `kafka-consumer-groups.sh --describe --group ledger-updaters-cloud` showed **zero active members**, with lag climbing unbounded (reached ~12.8k messages across 3 partitions) for at least 18 minutes after `DatabaseConnectivityMonitor` had already logged the DB connection itself as `RESTORED`. `transaction-processor` (KEDA-scaled, multiple replicas) degraded rather than fully stopped — 2 of 4 pods zombied the same way while the others kept consuming.

   Fixed by extending finding 6's exact retry-with-backoff-then-mark-`KafkaConsumerHealthState` pattern to these DB calls too (same 1s→15s Mutiny backoff, same 4-minute budget, same narrow `@Liveness` fail-stop only on exhaustion) in both `TransactionProcessor.process()` (`services/transaction-processor/.../TransactionProcessor.java`) and `LedgerUpdater.onCommitted()` (`services/ledger-service/.../LedgerUpdater.java`). A transient DB blip now retries and self-heals (via the same JDBC `socketTimeout`/`connectTimeout` fix) instead of killing the consumer on the very first attempt; only a genuinely exhausted retry budget still fails liveness for a real — and now actually necessary — restart. Confirmed live after redeploy: a full interconnect break/restore cycle no longer leaves any pod with a dead consumer — `ledger-updaters-cloud`'s ~12.8k backlog drained fully to 0 lag on its own with zero manual intervention, and `transactions-raw` correctly settled at 0 lag on all 6 partitions once caught up (verified this was genuine catch-up, not a stale display, by confirming offsets were static across repeated polls once TPS was at 0 — not a symptom of anything broken).

Also see the JDBC self-healing fix in Phase 2 Operational Notes below (`socketTimeout`/`connectTimeout` on `account-service`/`ledger-service`/`transaction-processor`'s datasources) — without it, a connection pool left holding stale connections from before a break never recovers even after these Listeners come back, requiring a manual pod restart; with it, Agroal detects and replaces dead connections within seconds automatically.

## Cluster Access

Two separate kubeconfig files — one per cluster. `oc` merges them natively at runtime via a colon-separated `KUBECONFIG` variable. **Never merge them into a single file.**

`onprem` and `cloud` are role names, not infrastructure — the two clusters may be on any provider or combination of providers (AWS, GCP, Azure, bare metal, etc.) and this varies between test runs. The actual cluster endpoints are environment-specific; `get-kubeconfig.sh` captures whatever the current `oc login` session points to and renames its context to `onprem` or `cloud` accordingly, so nothing else in the repo needs to know the real hostname.

| Context | Role |
|---|---|
| `onprem` | Hub / record-of-truth cluster (static capacity) |
| `cloud` | Spoke / elastic-burst cluster (scales to zero) |

**Interactive setup (one-liner):**
```bash
export KUBECONFIG="$(pwd)/kubeconfig-onprem:$(pwd)/kubeconfig-cloud"
oc config get-contexts   # should show both onprem and cloud
```

**All scripts auto-configure KUBECONFIG** — no export needed before running them. If you pre-export `KUBECONFIG`, your value is respected.

**Refreshing an expired token:**
```bash
# 1. oc login to the cluster's actual API endpoint (whatever provider it's on this run)
oc login https://api.<cluster-domain>:6443
# 2. Export the new credentials to the right file, renaming the context to onprem/cloud
./get-kubeconfig.sh onprem   # or: ./get-kubeconfig.sh cloud
```

`kubeconfig-onprem` and `kubeconfig-cloud` are in `.gitignore` — never commit them.

## Phase 0 Operational Notes

**OpenShift GitOps operator's default `ArgoCD` CR OOMs the application-controller on this RHACM-hub cluster — apply `infra/argocd/argocd-instance.yaml`:**
The `openshift-gitops-operator` auto-creates a default `ArgoCD` instance (name: `openshift-gitops`) with a `2Gi` controller memory limit and a `resource.exclusions` list that does **not** exclude `Event`/`events.k8s.io Event` objects. On a RHACM Hub cluster (401 CRDs from RHACM, RHACS, Tekton, cert-manager, KEDA, Strimzi, Crunchy PGO, Skupper, etc.) with two registered clusters (onprem in-cluster + `cloud` via an external `cluster-secret`), the application-controller's watch cache ends up holding every Event across both clusters for no diffing benefit — Events are high-churn and Argo CD Applications never target them — and it gets `OOMKilled` (confirmed live: `lastState.terminated.reason: OOMKilled`, exit 137, repeated `CrashLoopBackOff`). `infra/argocd/argocd-instance.yaml` fixes this as a **merge-patch** (only `spec.controller.resources`, `spec.controller.processors`, and `spec.resourceExclusions` are set — the operator keeps owning everything else): raises the memory limit to `4Gi` (node headroom is ~30Gi/node, so this is safe), caps reconciliation parallelism (`processors.status: 10` / `operation: 5`, defaults are ~20/~10) so a post-restart full-fleet sync storm can't spike memory as hard, and adds the missing `Event` exclusion on top of the operator's existing default exclusions (which are preserved verbatim in the same field, not replaced). Applied by `bootstrap-phase0.sh` right after the `openshift-gitops-server` readiness wait.

**`account-service` HPA `FailedGetResourceMetric`/`FailedComputeMetricsReplicas` events are almost always a transient `metrics-server` rollout, not an app bug:**
Confirmed live on both clusters: these warning events on the `account-service` HPA (`oc describe hpa account-service -n banking-demo`) coincide with `metrics-server` (namespace `openshift-monitoring`, owned by the `cluster-monitoring-operator`) getting rolled to a new ReplicaSet — triggered by OpenShift's own service-ca serving-certificate secret being recreated (`SecretCreated Secret/metrics-server-<hash> ... because it was missing`), which cascades into the old pods failing their readiness probe (HTTP 500) until the new cert-bearing generation comes up. `metrics-server` pods show `restartCount: 0` with no `OOMKilled` in `lastState` — this is platform certificate reconciliation, not a crash, and not related to the `ArgoCD` OOM above. During the rollout window the `metrics.k8s.io` aggregated API has no fresh data, so the HPA's ~15s metric-fetch cycle fails with `no metrics returned from resource metrics API`, then `did not receive metrics for targeted pods (pods might be unready)` as new pods come up but haven't been scraped yet. Nothing in `app-services/account-service/base/{deployment,hpa}.yaml` needs to change — resource requests are present and the `scaleTargetRef`/metric target are correct. Before assuming an app/manifest misconfiguration, confirm current health instead of trusting historical events: `oc get apiservices v1beta1.metrics.k8s.io` (expect `Available: True`) and `oc adm top pods -n banking-demo -l app=account-service` (expect live CPU/memory rows). If it recurs, `oc get events -n openshift-monitoring | grep metrics-server` shows the rollout/readiness-probe activity.

## Phase 1 Operational Notes

Issues discovered during Phase 1 deployment that must be kept in mind for future work:

**AMQ Streams 3.2 / Kafka 4.x only (no ZooKeeper):**
AMQ Streams 3.2 ships Strimzi 0.46, which dropped ZooKeeper entirely. Only Kafka 4.1.0 and 4.2.0 are supported. The `Kafka` CR must have `strimzi.io/node-pools: enabled` and `strimzi.io/kraft: enabled` annotations, no `spec.zookeeper`, no `spec.kafka.replicas`, no `spec.kafka.storage` — all node topology is defined via `KafkaNodePool` resources. Never use Kafka version 3.x in any manifest.

**Argo CD RBAC — admin RoleBinding required per managed namespace:**
The `openshift-gitops-argocd-application-controller` ServiceAccount (in `openshift-gitops`) has no default permissions in application namespaces. Before Argo CD can sync Kafka, PostgreSQL, or any other resource into `banking-infra`, a `RoleBinding` must exist that grants it the `admin` ClusterRole in that namespace. The `admin` ClusterRole aggregates Strimzi and Crunchy PGO rules automatically via operator-installed aggregation roles.

**Cloud cluster Argo CD registration — TLS insecure:**
On self-managed OCP the cloud cluster's API server certificate commonly covers `*.apps.*` SANs, not `api.*` (varies by installer/provider). The `cloud-cluster-secret` in `openshift-gitops` must set `tlsClientConfig.insecure: true`; providing `caData` from the cluster config view will fail with an x509 mismatch. Do not attempt to fix this by pulling a different CA — just keep `insecure: true`.

**Skupper AccessToken — PEM CA must use YAML literal block scalar:**
PEM certificates contain `-----END CERTIFICATE-----` lines that YAML parses as document separators (`---`) when embedded in a heredoc. The `spec.ca` field in the `AccessToken` CR must be written as a YAML literal block scalar (`ca: |`) with the PEM content indented. `bootstrap-phase1.sh` writes the token to a temp file using `sed 's/^/    /'` to indent the PEM rather than using a heredoc inline.

**MirrorMaker 2 v1beta2 API (Strimzi 0.46+) required fields:**
The `KafkaMirrorMaker2` CR with the new spec structure requires `spec.target.alias`, `spec.target.groupId`, `spec.target.configStorageTopic`, `spec.target.offsetStorageTopic`, `spec.target.statusStorageTopic`, and `spec.mirrors[].source.alias`. Missing any of these causes a validation error and the resource is never created. `spec.mirrors[].source.bootstrapServers` points to a dedicated Skupper tunnel (`kafka-bootstrap-mm2:9094`) — see the advertised-listener note immediately below for why this is a separate tunnel from the one everything else uses (`kafka-bootstrap:9092`).

**MirrorMaker 2 needs its own dedicated listener/tunnel — the shared `plain`/`tls` listeners cause it to silently mirror cloud's own Kafka instead of onprem's:**
Confirmed live (2026-09-04): onprem and cloud both run a Strimzi Kafka cluster named `banking-kafka` in the identically-named `banking-infra` namespace on each cluster — a deliberate consequence of `onprem`/`cloud` being symmetric logical roles (see top of this file). Kafka's `type: internal` listeners (`plain`/`tls`) advertise each broker at its in-cluster DNS name, e.g. `banking-kafka-broker-0.banking-kafka-kafka-brokers.banking-infra.svc.cluster.local` — confirmed live, this name resolves from a cloud pod to **cloud's own** broker-0 (`10.131.0.121`), not onprem's (`10.128.4.102`), because both clusters have a service by that exact name. A client that bootstraps through the Skupper `kafka-bootstrap` tunnel reaches onprem correctly for the first metadata request, but the broker's response then redirects it to that colliding hostname for actual fetches — so MirrorMaker2 silently ends up reading/writing cloud's own Kafka instead of onprem's ("self-replication" — this is what originally forced `replicas: 0` in commit `6dbb9e0`, mis-attributed at the time to a "GCP-local Kafka" bug specific to the old cloud provider; it's actually provider-agnostic and was still present after the migration to Azure).

Fixed with a dedicated `mm2` listener (`infra/kafka/base/kafka.yaml`, port 9094, `type: internal`) using `configuration.advertisedHostTemplate: banking-kafka-broker-{nodeId}-mm2` to give each broker a collision-free hostname — confirmed via Strimzi's own docs (`GenericKafkaListenerConfigurationBroker.adoc`): "Overriding the advertised host and ports is available for all types of listeners," including internal ones, specifically for cross-cluster tunnel scenarios. Tunnels it through 4 new Connector(onprem, `infra/skupper/onprem/connectors.yaml`)/Listener(cloud, `infra/skupper/cloud/listeners.yaml`) pairs — one bootstrap + one per broker — entirely separate from the existing `kafka-bootstrap`/`postgresql-primary`/`apicurio-registry` tunnel (which app services and the chaos-toggle feature keep using unchanged). `mirror-maker2.yaml`'s `source.bootstrapServers` now points at `kafka-bootstrap-mm2:9094`. Adding the listener triggers a rolling restart of all 3 onprem (and 3 cloud, since the listener is defined in the shared `base/kafka.yaml`) brokers — expected and safe, no data loss.

**Verified live with an actual traffic burst, not just a static offset check** (a static check can't distinguish "really mirroring onprem" from "coincidentally growing at a similar rate"): bumped the onprem generator to 20 TPS for 20s, then back to 0. `transactions-raw` partition offset deltas matched exactly on both clusters: partition 0 +131/+131, partition 1 +143/+143, partition 2 +146/+146. This rules out the self-replication bug definitively, not just "some data appeared" — cloud's copy is byte-for-byte tracking onprem's real production, one-for-one.

**`topicsPattern` must be exactly `"transactions-raw"`, never a wildcard like `"transactions-.*"` — a broader pattern silently double-persists every onprem-committed transaction into cloud's ledger:**
Confirmed live (2026-09-04, ~25 minutes after first re-enabling MM2): the original `topicsPattern: "transactions-.*"` (present in the manifest since before MM2 was ever disabled, carried forward unquestioned when fixing the advertised-listener bug above) matches all three `transactions-*` topics, not just `transactions-raw` — confirmed via the Kafka Connect REST API (`GET /connectors/.../config`) showing `"topics": "transactions-.*"` live on the running connector, and via a `ledger-updaters-cloud` consumer-group lag check (268k+ messages of accumulated `transactions-committed` backlog MM2 had pushed into cloud's local topic once the wildcard pattern took effect). `transaction-processor` has an `OWNED_PARTITIONS` guard specifically because `transactions-raw` is mirrored (see Phase 2 notes) — but `LedgerUpdater` (`ledger-service`, `@Incoming("committed-in")`) has **no equivalent guard**: no partition-ownership filter and no transaction-id idempotency pre-check (unlike `TransactionProcessor`'s `SELECT COUNT(*) FROM transactions WHERE transaction_id = ?1` check), and both onprem's and cloud's `ledger-service` write into the **same shared onprem `ledger_entries` table** (cloud's writes there too, via RHSI — see Phase 2 notes) — so this pattern is a real double-write hazard in general. In this specific incident, however, an actual exact-duplicate-row check (`GROUP BY account_id, running_balance, as_of, source_cluster HAVING count(*) > 1`, run across the whole table, not just a recent time window) came back **zero** — the rows cloud's `ledger-service` wrote while draining the mirrored backlog were for `onprem`-tagged events with no prior row at all (a pre-existing gap in onprem's own ledger history, unrelated to and predating this bug, cause not investigated), so this incident happened to backfill missing data rather than duplicate existing data. Don't take that as reassurance the hazard is safe to leave in place — a wildcard `topicsPattern` remains a correctness bug the moment `LedgerUpdater` and onprem's own ledger-service *do* overlap on the same event, which this incident's timing happened not to trigger. Fixed by narrowing to `topicsPattern: "transactions-raw"` — the only topic the architecture actually documents as DR-mirrored; `transactions-dlq` was also incidentally being mirrored with no cloud-side consumer for it either way, so excluding it too is strictly correct, not just incidental. Never caught before because MM2 was `replicas: 0` for the entire time `LedgerUpdater` has existed.

Applying this kind of fix hits Argo CD's `selfHeal: true` head-on: a direct `oc apply` of the corrected manifest gets silently reverted back to the old (buggy) live state within seconds if Argo hasn't yet polled the git commit that changes it — confirmed live (its default poll interval left it on the prior commit for a couple of minutes after the fix was pushed). Committing and pushing is necessary but not sufficient for an urgent fix; force an immediate reconcile instead of waiting out the poll interval: `oc annotate application.argoproj.io <name> -n openshift-gitops argocd.argoproj.io/refresh=hard --overwrite`.

**No routes on cloud cluster from Phase 1 is correct:**
The cloud Skupper site uses an empty spec (outbound link initiator — no `linkAccess`). Kafka has internal-only listeners. Apicurio is onprem-only. The absence of routes in `banking-infra` on cloud after Phase 1 is expected behaviour.

**RHSI does not ship an OpenShift `ConsolePlugin` — the real UI is the certified `skupper-netobs-operator`:**
The installed Red Hat Service Interconnect operator (`skupper-operator.v2.2.2-rh-1`) registers no `console.openshift.io/plugins` CSV annotation and creates no `ConsolePlugin` object — confirmed via `oc get consoleplugin` (only unrelated OCP-native plugins are present). The real network-visibility UI ships as a separate, version-paired Red Hat-certified operator: `skupper-netobs-operator` (displayName "Red Hat Service Interconnect Network Observer"), channel `stable-2`, always released in lockstep with `skupper-operator` (both were `v2.2.2-rh-1` at time of writing). It is a Helm-based operator (`helm.sdk.operatorframework.io/v1`) owning the `NetworkObserver` CRD (`observability.skupper.io/v2alpha1`); its CR spec fields are field-for-field identical to the upstream `network-observer` Helm chart's `values.yaml`. Chart/CRD defaults are **not** OpenShift-ready (`auth.strategy` defaults to `basic`, `tls.openshiftIssued` defaults to `false`, `route.enabled` defaults to `false`) — `infra/skupper-netobs/network-observer.yaml` explicitly overrides these to `auth.strategy: openshift`, `tls.openshiftIssued: true`, `route.enabled: true`, matching the CSV's own `alm-examples` recommended sample.

**One Network Observer instance sees the whole multi-site network — deploy once, on onprem:**
`NetworkObserver.spec.router.endpoint` defaults to `amqps://skupper-router-local`, the local AMQP management endpoint every `skupper-router` exposes in its own namespace. Since both sites' routers are already linked into one mesh (`sites.skupper.io` reports `SITES IN NETWORK: 2` on both onprem and cloud), a single Network Observer attached to either router's local endpoint observes the entire linked network — flow/topology data propagates through the already-established router mesh. It does not need to be deployed per-cluster. `bootstrap-phase1.sh` deploys it once, on onprem, namespace `banking-infra` (alongside the onprem `skupper-router`), after the cross-cluster link is confirmed established.

**`NetworkObserver` readiness — poll condition `Deployed`, not a custom status field:**
This CRD only exposes the four standard `operator-sdk` Helm-operator conditions (`Initialized`, `Deployed`, `ReleaseFailed`, `Irreconcilable`) — `Deployed: True` (reason `InstallSuccessful`) is the terminal "done" signal and correlates directly with the Deployment becoming Ready; there is no separate `Available` condition on this CRD (contrast with `Central` below, which has both).

**Getting the Network Observer console URL:**
```bash
oc --context onprem get route skupper-network-observer -n banking-infra -o jsonpath='https://{.status.ingress[0].host}{"\n"}'
```
Login is OpenShift OAuth (`auth.strategy: openshift` in `infra/skupper-netobs/network-observer.yaml`) — use your normal OpenShift username/password, there is no separate credential to fetch.

**IMPORTANT — this Route uses `spec.subdomain`, not `spec.host`; the real hostname only lives under `.status.ingress[0].host`:**
`infra/skupper-netobs/network-observer.yaml` sets `route.subdomain: network-observer` (not `route.host`), so OpenShift's router assigns and writes the actual hostname only after admitting the Route — `.spec.host` stays empty forever on a subdomain-based Route. `oc get route ... -o jsonpath='{.spec.host}'` silently returns an empty string (looks like success, prints `https://`). Always read `.status.ingress[0].host` instead. This bit `bootstrap-phase1.sh`'s own "Network console:" printout until fixed — confirmed live (`.spec.host` empty, `.status.ingress[0].host` correct). Central's Route (RHACS) is unaffected — it uses a plain generated `spec.host`, not a subdomain.

**Re-applying an existing `AccessToken` CR does NOT recreate its Secret — only a fresh create does:**
Confirmed live while manually recovering the link during early testing of the dashboard's link-failure feature (before it was redesigned to target Skupper Listeners instead of the Link CR — see the Chaos Scenario section above; this note is kept as a standalone Skupper operational fact, no longer tied to `LinkResource.java`'s current behavior). Recovering a severed RHSI link by re-running `bootstrap-phase1.sh` Step 6's `oc apply -f` against an `AccessToken` object that still exists (e.g. its backing Secret was deleted but the `AccessToken`/`Link` CRs were left in place) updates (`configured`, not `created`) the object's spec and does successfully re-establish the `Link` (`status.conditions[type=Ready]` flips `True`, `SITES IN NETWORK` count is correct) — but the operator does **not** recreate the `kubernetes.io/tls` Secret named after it (`onprem-link-token`) that the Link's `spec.tlsCredentials` references. The Secret is only materialized on a genuine `AccessToken` **create**. The correct manual recovery sequence when the Secret is gone but the `AccessToken`/`Link` objects survived: `oc delete accesstoken,link onprem-link-token -n banking-infra --context cloud` first, then re-run the AccessGrant/AccessToken exchange (also delete+recreate the `AccessGrant` `cloud-link-grant` on onprem — it's `redemptionsAllowed: 1`, so a once-redeemed grant issues no new code on a bare re-apply either).

## Phase 2 Operational Notes

Issues discovered during Phase 2 deployment that must be kept in mind for future work:

**Apicurio serde package name — singular `serde`, not plural `serdes`:**
The BOM-managed `apicurio-registry-serdes-avro-serde-2.5.9.Final.jar` (pulled via `quarkus-apicurio-registry-avro`) places its classes under the package `io.apicurio.registry.serde.avro` (singular). Any `application.properties` referencing `io.apicurio.registry.serdes.avro` (plural) causes `ClassNotFoundException` at startup. All three services — `transaction-generator`, `transaction-processor`, `ledger-service` — must use the singular form for both serializer and deserializer class names.

**`@Blocking @Transactional` incompatible with SmallRye reactive messaging in Quarkus 3.9.5:**
Combining `@Blocking` and `@Transactional` on a `@Incoming` message handler causes Agroal's `LocalXAResource.commit()` to find `enlisted=false`, throwing `RollbackException: Enlisted connection used without active transaction`. The channel enters permanent `fail-stop` state. Fix: remove `@Transactional` from the handler and wrap the database work in `QuarkusTransaction.requiringNew().call(() -> { ... })`. Add `quarkus-narayana-jta` as an explicit compile dependency in `pom.xml` (it is pulled transitively but the `QuarkusTransaction` API requires it on the compile classpath).

**Hibernate 6 sequence naming — `ledger_entries_seq` must be lowercase, unquoted:**
Hibernate 6 `SequenceStyleGenerator` (Quarkus Panache) generates `select nextval('ledger_entries_SEQ')`. PostgreSQL casts that string to `regclass` by folding it to lowercase → looks for `ledger_entries_seq`. The `bootstrap-phase2.sh` schema SQL block must create the sequence **without double quotes**: `CREATE SEQUENCE IF NOT EXISTS ledger_entries_seq START 1 INCREMENT BY 50;`. Using `"ledger_entries_SEQ"` (double-quoted) creates a case-sensitive object that `nextval()` cannot find, crashing ledger-service on first persist. Also, the `ledger_entries` table primary key column must be named `id` (not `entry_id`) to match the `PanacheEntity.id` field mapping.

**Kafka PVC disk retention — always set both `retention.ms` AND `retention.bytes`:**
At 100 TPS with 6 partitions and replication factor 3, a 20 Gi broker PVC fills in under an hour with only a time-based retention limit. When MirrorMaker 2 reconnects after a link outage it replays backlog at full speed, accelerating the fill. Always configure both `retention.bytes` (per partition) and `segment.bytes` (smaller segments let the log cleaner enforce retention more frequently) in the `KafkaTopic` Strimzi CRs. Current values: `transactions-raw` — 2 h / 128 MB / 32 MB segments (per-partition, across 24 partitions since the 2026-09-05 partition-count increase); `transactions-committed` — 2 h / 250 MB / 64 MB segments. Dynamic configs applied via `kafka-configs.sh` are lost when broker PVCs are wiped; the `KafkaTopic` CR is the only persistent source of truth.

**Cloud `transaction-processor` must use the local cloud Kafka, not the Skupper Listener:**
Both `KAFKA_BOOTSTRAP_SERVERS` (Deployment env var) and `bootstrapServers` (KEDA ScaledObject trigger) in the cloud overlay must be set to `banking-kafka-kafka-bootstrap.banking-infra.svc.cluster.local:9092` — the Strimzi bootstrap service of the cloud-local Kafka cluster. Setting them to `kafka-bootstrap.banking-infra.svc.cluster.local:9092` (the Skupper Listener that tunnels to the onprem Kafka) causes KEDA to fail with "client has run out of available brokers" and breaks the chaos-resilience property: when the RHSI link is severed the cloud processor must continue consuming from its local Kafka replica, not fall over with the link.

**`grep -P` (Perl regex) is not available on macOS:**
Bootstrap script checkpoint sections must use `grep -qE` instead of `grep -qP`. BSD grep (macOS default) does not support the `-P` flag; every check silently fails and the checkpoint reports all deployments as down even when they are fully healthy. `grep -qE '[1-9]'` is POSIX-compatible and works on both Linux and macOS.

**Cloud app services all connect to onprem PG via RHSI — never the local cloud PGO:**
All cloud application services (`account-service`, `transaction-processor`, `ledger-service`) connect to the onprem PostgreSQL primary via the RHSI Skupper listener at `postgresql-primary.banking-infra.svc.cluster.local:5432`. The cloud PGO instance (`postgres-primary`) runs independently with no application schema and a separate PGO-managed password. Do not point any cloud service DATASOURCE_URL at `postgres-primary`; use `postgresql-primary` in every cloud overlay.

**`postgresql-credentials` on cloud must carry the onprem PGO password:**
The `postgresql-credentials` secret in `banking-demo` on cloud must be populated with the onprem PGO password (from `postgres-pguser-postgres` in `banking-infra` on onprem), because all cloud services authenticate against the onprem PostgreSQL via RHSI. Using the cloud-local PGO password causes `FATAL: password authentication failed` on every cloud service. `bootstrap-phase2.sh` applies the same onprem password to both clusters.

**`transaction_id` Avro String must be cast to `java.util.UUID` before native INSERT:**
The `TransactionEvent` Avro schema declares `transactionId` as Avro `string`, so `getTransactionId()` returns a Java `String`. PostgreSQL's `UUID` column type rejects a bound `character varying` parameter without an explicit cast. The native INSERT in `TransactionProcessor.java` must pass `UUID.fromString(event.getTransactionId())` as parameter 1. Binding the raw `String` causes `ERROR: column "transaction_id" is of type uuid but expression is of type character varying` and puts the pod in CrashLoopBackOff on both clusters.

**RESTEasy Reactive dispatches JAX-RS methods on the event loop — add `@Blocking` for blocking I/O:**
In Quarkus 3.x with RESTEasy Reactive, resource methods that return plain (non-reactive) types are still dispatched on the Vert.x event loop by default. Any method that performs blocking I/O (e.g. `java.net.http.HttpClient.send()`, synchronous REST calls) must be annotated with `@Blocking` (`io.smallrye.common.annotation.Blocking`) so the call is dispatched to a worker thread. Without it the event loop stalls and Vert.x's blocked-thread-checker fires repeated WARNs.

**Partition ownership prevents silent balance double-apply caused by MM2 replication:**
MM2 replicates every message from onprem Kafka → cloud Kafka. With two independent consumer groups each reading from their local Kafka, every onprem-originated transaction was processed by BOTH clusters — `ON CONFLICT DO NOTHING` only prevents a duplicate DB row; it does NOT prevent `account-service.apply()` being called twice, silently corrupting account balances. Fix: split the `transactions-raw` partitions between clusters (onprem owns 0-11; cloud owns 12-23 — 24 partitions total as of the 2026-09-05 partition-count increase, up from an original 6/3-per-cluster split that silently capped KEDA's real scaling ceiling far below `maxReplicaCount`, see "KEDA's Kafka scaler silently caps replicas at the topic's partition count" below). Both `transaction-generator` and `transaction-processor` read `OWNED_PARTITIONS` from an env var (default is the full partition list — safe for local dev; overlays pin cluster-specific values). Generator uses `OutgoingKafkaRecordMetadata.withPartition(computePartition(accountId))` to restrict output to owned partitions. Processor handler signature changed from `void process(TransactionEvent)` to `CompletionStage<Void> process(Message<TransactionEvent>)` with `@Acknowledgment(Acknowledgment.Strategy.MANUAL)`; non-owned partitions are fast-ACKed via `return message.ack()` without processing. KEDA scaling remains correct because fast-ACKed partitions contribute ~0 to total consumer group lag.

**Traffic weight controls generation-rate split only — Kafka partition ownership is permanently static:**
`PUT /api/gateway/traffic-weight` (cluster-gateway) only stores/reports the configured weight (`AtomicInteger trafficWeight`, via `GET /api/gateway/traffic-weight` and `metrics/summary`) — it no longer reassigns Kafka partitions. `OWNED_PARTITIONS` (onprem `0-11`, cloud `12-23`, set by the Kustomize overlays) never changes at runtime, which is what keeps the MM2 double-apply guard above correct and simple.

The actual traffic-split mechanism lives in `dashboard-backend`'s `DashboardResource`: `PUT /api/backend/traffic-weight` fans the weight out to both cluster-gateways and stores it in a backend-authoritative `AtomicInteger currentTrafficWeight`; `PUT /api/backend/generator/tps/{total}` (driven by the Load Control panel) reads that weight and derives the per-cluster TPS split from it — proportional (`onpremTps = round(total × weight / 100)`) for any weight ≠ 100, or the capacity-based "Auto Burst" rule (`onpremTps = min(total, onprem.capacity.tps)`, cloud absorbs the remainder) specifically at weight = 100. `onprem.capacity.tps` (default `100`) is a `dashboard-backend` config property, the single source of truth also threaded to the frontend via `MetricsPayload.onpremCapacityTps` so displayed capacity lines never drift from the backend value. This previously used a hardcoded `min(total,100)/max(0,total-100)` rule that ignored the configured weight entirely — fixed because it made "Traffic Split" not actually control transaction distribution, and because the old partition-reassignment mechanism could leave a cluster owning zero partitions at weight=100/0, silently dropping any TPS routed to it (the generator's `if (partition < 0) continue` guard).

The 7-step slider in `ChaosPanel.tsx` (0/17/33/50/67/83/100%) is now purely a UX choice — it no longer corresponds to partition-count granularity, since partitions don't move.

**KEDA's Kafka scaler silently caps replicas at the topic's partition count — confirmed live, root cause of `transaction-processor` never scaling past 6-7 despite tens of thousands of messages of backlog:**
`transactions-raw` originally had 6 partitions, split 3-per-cluster via `OWNED_PARTITIONS` (see above). The `transaction-processor` `ScaledObject` (`app-services/transaction-processor/base/scaledobject.yaml`) has always set `maxReplicaCount: 20`, but neither it nor anywhere else in this repo sets `allowIdleConsumers: true` on the Kafka trigger — so KEDA's Kafka scaler applies its documented default behavior of never authorizing more consumers than the topic has partitions, since a consumer beyond that count could never be assigned a partition by Kafka's own one-consumer-per-partition rule and would sit permanently idle. With only 6 total partitions, the real ceiling was 6 per cluster, not 20 — confirmed live (2026-09-05) three ways: (1) `oc get --raw /apis/external.metrics.k8s.io/.../s0-kafka-transactions-raw` on cloud returned a metric value of exactly `3000` (= 6 partitions × `lagThreshold` 500) while the true consumer-group lag was over 128,000 (partitions 3/4/5 individually carrying ~50-52k lag each) — KEDA's clamp caught mid-act; (2) cloud's HPA 3-day event history never showed a rescale above 7 across dozens of scaling events despite `maxReplicaCount: 20` having been in place since commit `ff61990`; (3) onprem's true lag (~2,650-2,800) sat just under its own 6×500=3000 cap, on the same trajectory. `lagThreshold: 500` itself was not the bug (deliberately set in commit `419b525`, consistent with `bootstrap-phase2.sh`/`LoadControlPanel.tsx`), and the generator's `computePartition` hashing was checked and ruled out too (cloud's three owned partitions were evenly loaded, ~50-52k lag each — no skew).

Fixed by increasing `transactions-raw` to 24 partitions (`infra/kafka/base/topics.yaml`), giving each cluster 12 owned partitions (4x the real concurrency) instead of 3, with `retention.bytes`/`segment.bytes` scaled down proportionally (128 MB / 32 MB per partition) to keep the topic's total broker disk footprint roughly flat. `OWNED_PARTITIONS` updated everywhere (both overlays and the Java `getOrDefault` fallbacks in `TransactionGeneratorService`/`TransactionProcessor`) to the new 0-11/12-23 split. `KafkaPartitionStats.PARTITIONS` (transaction-processor, backs `GET /api/processor/stats/partition-lag`) and `ChaosPanel.tsx`'s `PartitionMap` (`onpremCount` estimate and the rendered box count) both independently hardcoded `6` and needed the same update, or the partition-lag visualization would have silently truncated at partition 5 forever, even after the topic itself moved on. MirrorMaker 2's source connector also got an explicit `sourceConnector.tasksMax: 4` (`infra/mirrormaker2/mirror-maker2.yaml`, previously absent/implicit-default-1) since replication throughput needs to scale with the 4x partition increase too. No change was needed to `scaledobject.yaml` itself — with 24 real partitions, KEDA's own ceiling (24) is now above `maxReplicaCount` (20), so the configured max is finally the active constraint instead of a silent partition-count clamp.

Migration note: the partition-count increase was done via delete-and-recreate of the `KafkaTopic` CR (not an in-place partition increase) specifically to avoid a hazard — an in-place increase leaves old messages at their original low partition numbers, and if the new ownership ranges don't happen to nest the old ones identically per cluster, previously-cloud-owned messages could suddenly fall inside onprem's widened range (or vice versa) and re-trigger the double-apply bug this whole `OWNED_PARTITIONS` mechanism exists to prevent. Since `transactions-raw` is synthetic, disposable demo data, deleting and recreating the topic on both clusters (each runs its own independent physical copy — see the MM2 advertised-listener notes above) was safe and simpler than draining first.

**Fix re-verified live end-to-end (2026-09-05), not just via manifest inspection:** after cutover (topic recreated at 24 partitions on both clusters, `OWNED_PARTITIONS`/`KafkaPartitionStats.PARTITIONS`/`ChaosPanel.tsx` all rebuilt and rolled out), drove a real 300 TPS test (100 onprem / 200 cloud via the Auto Burst split) through each cluster's own `cluster-gateway`. Onprem scaled to **17 replicas** and cloud hit the full **20-replica `maxReplicaCount` ceiling** — both far past the old hard-capped 6-7. The external metric (`s0-kafka-transactions-raw`) read `12k` during the test — a real, load-driven value, not the old fixed `3000` clamp — confirming KEDA is no longer silently ceiling-limited by partition count. `kafka-consumer-groups.sh --describe` showed lag spread evenly across all 12 owned partitions per cluster (not just 3), and after stopping the test load, backlog on cloud drained cleanly to **0 lag on all 24 partitions** with replicas scaling back down — confirming both directions (scale-up under load, scale-down at idle) work correctly post-fix. One transient false alarm during verification: a `kafka-consumer-groups.sh` snapshot taken mid-rebalance (right after an HPA scale-down event) briefly showed inflated lag (83,573) while KEDA's own external metric simultaneously read `0` for the same group — an artifact of describing a consumer group while it's mid-reassignment, not a real regression; a fresh snapshot moments later showed 0 lag on every partition, matching KEDA's reading.

**Quarkus `@CacheInvalidate` key must match `@CacheResult` key — use `@CacheKey` to select the right parameter:**
When `@CacheResult` is on a method with one parameter, the cache key is that parameter directly. When `@CacheInvalidate` is on a method with multiple parameters, the default key includes ALL parameters. If the write method has a different signature than the read method (e.g., `applyDelta` takes `accountId` + `body` Map while `getBalance` takes only `accountId`), add `@CacheKey` to the matching parameter on the write method to restrict the invalidation key to `accountId` alone. Without `@CacheKey`, the composed key `(accountId, body)` never matches the `@CacheResult` key `(accountId)` and the cache is never invalidated.

**Optimistic locking on balance update — version column, request body type, and idempotency pre-check:**
The `accounts` table carries a `version BIGINT NOT NULL DEFAULT 0` column. Every successful `UPDATE` atomically increments it (`version = version + 1`) and includes it in the `WHERE` clause (`AND version = :version`) when the caller supplies one. Account-service returns the current version in every `apply` response (success, insufficient funds, and version conflict). On version conflict (0 rows updated and DB version ≠ submitted version), the response carries `reason: "version conflict"` and the current DB version so the caller can retry immediately without an extra GET.

The `AccountServiceClient` body type must be `Map<String, Number>` (not `Map<String, Double>`) because the map carries both a `Double` delta and a `Long` version. Using `Map<String, Double>` forces a lossy cast on the version. Build the map with `new HashMap<>()` and `put` both values rather than `Map.of()` when the version entry is conditional — `Map.of` with mixed `Double`/`Long` values infers an intersection type that does not satisfy `Map<String, Number>` without explicit casts.

`ON CONFLICT DO NOTHING` on the `transactions` INSERT only prevents a duplicate row — it does NOT prevent `account-service.apply()` being called again on Kafka redelivery, which would corrupt the balance. The correct guard is a transaction-id pre-check BEFORE calling account-service: query `SELECT COUNT(*) FROM transactions WHERE transaction_id = ?1` inside `QuarkusTransaction.requiringNew()` and fast-ACK if the row already exists. The version cache (`ConcurrentHashMap<String, Long>`) in the processor stores the last known version per accountId, eliminating the extra GET call on every apply; it is populated from the `version` field in the `ApplyResponse`.

**DLQ Avro schema — use `string` for shared enum fields to avoid cross-schema type conflicts:**
When a new Avro schema (e.g., `TransactionFailed`) needs a field whose type is an enum defined in another schema (`TransactionType` in `TransactionEvent.avsc`), do NOT redefine the enum inline (avro-maven-plugin duplicate type error) and do NOT reference it by fully-qualified name (fragile cross-schema resolution at runtime). Use `"type": "string"` for the field and call `.name()` on the enum value at the call site (e.g., `event.getType().name()`). Simpler, avoids all cross-schema dependency, and the string value is human-readable in the DLQ topic.

**`bootstrap-phase2.sh` schema registration loop must include every Avro schema in `services/avro-schemas/`:**
Step 7 registers schemas explicitly with Apicurio so backward-compatibility enforcement is active before any pod starts. Any new `.avsc` file must be added to the `for schema in TransactionEvent TransactionCommitted TransactionFailed; do` loop. Without it the schema is only registered via `auto-register=true` on first emit — which works but bypasses compatibility checks until the first real message is produced.

**DLQ counter pattern — in-memory `AtomicLong` + `ConcurrentHashMap`, exposed via REST, proxied through cluster-gateway:**
To surface per-cluster rejection counts on the dashboard without a separate consumer service: track counts in the processor with `AtomicLong rejectedCount` and `ConcurrentHashMap<String, AtomicLong> rejectedByReason`; expose via `GET /api/processor/stats` (`ProcessorStatsResource`). The cluster-gateway proxies this as `GET /api/gateway/processor/stats` using the same `java.net.http.HttpClient` pattern as the existing `scaling/summary` proxy. `ClusterPoller` in dashboard-backend polls the gateway endpoint and adds `rejectedTotal` to `ClusterMetrics`/`MetricsPayload`. This avoids adding a Kafka dependency to dashboard-backend.

**Maven `target/` directories must never be committed — add `**/target/` to `.gitignore`:**
All Quarkus service Dockerfiles use multi-stage builds that copy only `pom.xml` and `src/`; Maven runs entirely inside the Docker build stage. The local `target/` directory is never read from the repository. Remove any committed `target/` content with `git rm -r --cached services/*/target` and add `**/target/` to `.gitignore`. Committing build artifacts wastes space, pollutes diffs, and gives a false impression that pre-compiled classes are required.

**Pod restart ≠ image rebuild — only `bootstrap-phase2.sh` (Tekton) rebuilds images:**
In OpenShift, restarting a pod (`oc rollout restart` or deleting a pod) causes the node to re-pull the existing image tag from the registry — it does NOT trigger a new build. Source code changes only take effect after a new Docker image is built and pushed. Run `bootstrap-phase2.sh` to trigger Tekton PipelineRuns for all 7 services. After builds complete, Argo CD detects the new image digest and automatically rolls out updated pods. If you restart a pod expecting to see code changes and nothing changes, the image has not been rebuilt.

**Cloud-local PostgreSQL replica for read-only queries — named Agroal datasource pattern:**
The cloud PGO streaming standby (`postgres-ha.banking-infra.svc.cluster.local:5432`) replicates the full onprem database including `pg_authid`, so the same `DATASOURCE_USER`/`DATASOURCE_PASSWORD` credentials (onprem PGO password) work directly on the cloud replica without crossing the Skupper tunnel. Verify the replica has data before relying on it: `oc exec -n banking-infra --context cloud <pg-pod> -- psql -U postgres postgres -c 'SELECT count(*) FROM accounts;'` should return 100.

**IMPORTANT — standby mode must be enabled before `DATASOURCE_READ_URL` is set in cloud overlays:**
The cloud `PostgresCluster` CR requires `spec.standby.enabled: true` before the read-replica path works. Without standby mode the cloud PGO is an independent cluster with its own PGO-managed password — different from the onprem password in `postgresql-credentials`. Setting `DATASOURCE_READ_URL=postgres-ha…` while standby is inactive causes `FATAL: password authentication failed` every few seconds, the Quarkus health check for the "read" datasource reports DOWN, and pods never become ready. To guard against this, `application.properties` must always include `quarkus.datasource."read".health-enabled=false` so a failed read replica cannot block pod readiness. Until `spec.standby` is configured and replication has caught up, do not add `DATASOURCE_READ_URL` to the cloud overlay — the fallback to `${DATASOURCE_URL}` (RHSI to onprem primary) keeps the service functional.

**PGO v5 standby mode requires a shared pgBackRest repository (S3, GCS, or Azure):**
The standby `PostgresCluster` bootstraps itself by running `pgbackrest restore` from the same repository as the primary. Local PVC-backed repos (`repo1.volume`) cannot be shared across clusters — each cluster's volume is inaccessible to the other. The only supported shared repo types in PGO v5 are `s3`, `gcs`, and `azure`. To enable standby: add a second repo (e.g., `repo2`) of type `s3` or `gcs` to the onprem `PostgresCluster`, let PGO back up to it, then configure the cloud `PostgresCluster` with the same repo and `spec.standby.enabled: true` / `spec.standby.repoName: repo2`. Once replication is streaming and `pg_authid` is replicated, the onprem PGO password works on `postgres-ha` and `DATASOURCE_READ_URL` can be restored in the cloud overlays.

To split reads from writes in Quarkus without a second Hibernate ORM persistence unit, add a named Agroal datasource in `application.properties`:
```
quarkus.datasource."read".db-kind=postgresql
quarkus.datasource."read".jdbc.url=${DATASOURCE_READ_URL:${DATASOURCE_URL:jdbc:postgresql://localhost:5432/postgres}}
quarkus.datasource."read".username=${DATASOURCE_USER:postgres}
quarkus.datasource."read".password=${DATASOURCE_PASSWORD:postgres}
```
Inject it with `@Inject @DataSource("read") AgroalDataSource readDataSource` and use raw JDBC (`Connection`/`PreparedStatement`/`ResultSet`) for SELECT queries. Panache static methods (`Entity.findById`, `Entity.count`) only work with the default datasource — replace them with raw JDBC on the read path. Add `@Blocking` to any JAX-RS method that opens a JDBC connection; without it RESTEasy Reactive dispatches on the event loop and JDBC stalls it. `DATASOURCE_READ_URL` defaults to `${DATASOURCE_URL}` so onprem services and local dev use a single datasource with zero code impact.

`@Scheduled` methods that previously used `@Transactional` + Panache for a count query can drop both annotations when replaced with raw JDBC — plain JDBC does not need a JTA transaction context.

The PGO service name for the cloud standby is `postgres-ha` (PgBouncer HA service, recommended entry point). Confirm with `oc get svc -n banking-infra --context cloud | grep postgres` before deploying — use `postgres-replicas` as a fallback if `postgres-ha` is absent. Do NOT use `postgres-primary` on cloud; that name is reserved for the Skupper Listener that tunnels to the onprem primary (`postgresql-primary` is the Skupper service; `postgres-primary` is the PGO local service — they have different names but the CLAUDE.md warning was about credential mismatch, not the hostname itself).

Chaos resilience benefit: routing reads to the local replica means balance lookups and ledger counts survive a Skupper link failure — only write operations (`POST /apply`, ledger entry inserts) circuit-break when the tunnel is severed.

**Quarkus Agroal named datasource health check — use `health-enabled` (kebab-case), not `health.enabled`:**
The Agroal extension config key for disabling a named datasource health check is `quarkus.datasource."<name>".health-enabled=false` — hyphen, not dot. Using `health.enabled` (dot notation) is silently ignored with a startup WARN `Unrecognized configuration key`, leaving the health check enabled. Verify with `grep health /application.properties` and ensure the hyphen form is present.

**WebSocket broadcasting in Quarkus WebSockets Next 3.9.5 — use explicit connection registry, not BroadcastProcessor:**
`BroadcastProcessor.create()` (Mutiny) retains subscriptions for disconnected WebSocket clients indefinitely. When Quarkus tries to send to a closed connection, it logs `ERROR: Unable to send text message from Multi: WebSocket is closed` every second per stale client, forever. `OpenConnections` (the idiomatic fix in newer Quarkus) does not exist in 3.9.5. The correct pattern for this version:
- Broadcaster holds `ConcurrentHashMap.newKeySet()` of `WebSocketConnection` instances
- `@WebSocket` endpoint declares `WebSocketConnection connection` as a **method parameter** on `@OnOpen` and `@OnClose` — **never via `@Inject` field**
- `publish()` calls `connections.removeIf(WebSocketConnection::isClosed)` then `conn.sendText(json)` for each remaining connection
This completely eliminates the Multi/BroadcastProcessor and the orphaned-subscription problem.

**CRITICAL — `@WebSocket` endpoint must receive `WebSocketConnection` as a method parameter, not via `@Inject`:**
`@WebSocket` endpoints default to `@Singleton` scope in Quarkus WebSockets Next when no scope annotation is present. `WebSocketConnection` is a `@ConnectionScoped` normal CDI scope, so `@Inject WebSocketConnection connection` gives a CDI client proxy — not the actual connection object. Every call to `broadcaster.register(connection)` adds the same proxy to the set. When `MetricsBroadcaster.publish()` calls `isClosed()` on the proxy from the scheduler thread (no active connection scope), it throws `ContextNotActiveException`. This exception propagates out of `removeIf` and is silently swallowed by `ClusterPoller.poll()` — no data ever reaches the frontend, even though the WebSocket shows "Live". The fix: declare `WebSocketConnection connection` as a method parameter on `@OnOpen` and `@OnClose`. The Quarkus WebSockets Next runtime passes the actual backing instance via method parameters, bypassing CDI proxy mechanics. The stored object is then safe to call from any thread (including `@Scheduled` methods).

**`transaction-processor` requires `quarkus-rest` + `quarkus-rest-jackson` in pom.xml — REST endpoints are silently dead without it:**
`transaction-processor/pom.xml` originally only had `quarkus-rest-client-jackson` (outbound REST client) but NOT `quarkus-rest` (inbound HTTP server). All `@Path`-annotated methods in `ProcessorStatsResource` compiled correctly but were never registered as routes — every call returned 404. The gateway's catch block silently fell back to `{"rejectedTotal":0}`, masking the bug for the entire session. The Quarkus installed features log (`INFO [io.quarkus] started in Xs. Installed features: [...]`) is the fastest diagnostic: `rest` must appear in the list. If it is absent, add both `quarkus-rest` and `quarkus-rest-jackson` to pom.xml. This affected `GET /api/processor/stats` (rejectedTotal always 0) and `GET /api/processor/stats/partition-lag` (Kafka lag data never flowing).

**Kafka per-partition consumer lag via AdminClient — use `@Startup` + background scheduler, never on-demand HTTP path:**
`KafkaPartitionStats` (in `transaction-processor`) uses `org.apache.kafka.clients.admin.AdminClient` to fetch per-partition consumer group lag for the partition map visualization. Key lessons:
- `AdminClient.create()` is non-blocking; the actual Kafka calls take 2–4 s on a cold connection.
- Use `@Startup` (`io.quarkus.runtime.Startup`) alongside `@ApplicationScoped` to force eager CDI initialization at pod start. Without it, the bean is lazily initialized only on the first HTTP request, and the background refresh never starts in time.
- Run the AdminClient calls in a `ScheduledExecutorService` (daemon thread, every 3 s) so `getLag()` is always a sub-millisecond volatile read, never blocking the HTTP request path. The timeout chain (ClusterPoller 400 ms → gateway 800 ms) would always expire before a cold AdminClient call completes.
- Launch both futures concurrently (`listOffsets` and `listConsumerGroupOffsets`) before calling `get()` on either — halves worst-case from 8 s to 4 s.
- Use a plain static POJO class with public fields and no-arg constructor for the `PartitionLag` return type — nested Java records may not be picked up by Quarkus's build-time Jackson scan and serialize as `{}` silently.

**Avro schemas must be placed in each service's `src/main/avro/` — the shared `services/avro-schemas/` directory is not used by Maven:**
The avro-maven-plugin in each Quarkus service reads `.avsc` files from `src/main/avro/` inside that service's directory. The Dockerfile copies only `pom.xml` and `src/` into the Docker build stage — the top-level `services/avro-schemas/` directory is never copied and is invisible to Maven. Adding a new schema only to `services/avro-schemas/` causes a `cannot find symbol` compilation failure in Tekton. The correct procedure for any new Avro type used by a service:
1. Add the `.avsc` file to `services/avro-schemas/` (for Apicurio bootstrap registration)
2. Copy the same file to `services/<service-name>/src/main/avro/` for every service that imports the generated class
`TransactionFailed.avsc` must exist in both `services/avro-schemas/` AND `services/transaction-processor/src/main/avro/` — the former for Apicurio, the latter for the Maven build.

**RHACS Central + SecuredCluster on both clusters (onprem self-monitors, cloud is remote) — no `InitBundle` CRD, use Central's REST API:**
The `rhacs-operator` CSV only owns `Central` and `SecuredCluster` CRDs — there is no CR-based shortcut for cluster registration. The scriptable mechanism is Central's own REST API: `POST https://<central-route>/v1/cluster-init/init-bundles` (Basic Auth `admin:<password>`, JSON body `{"name":"<cluster>"}`) returns a `kubectlBundle` field (base64-encoded YAML) which, applied via `oc apply -f -` on the target cluster's `stackrox` namespace, creates the `sensor-tls`, `collector-tls`, and `admission-control-tls` secrets `SecuredCluster` needs. This applies to **both** clusters — onprem gets its own bundle/`SecuredCluster` (`infra/rhacs/secured-cluster-onprem.yaml`) for self-monitoring, in addition to cloud's (`infra/rhacs/secured-cluster.yaml`). `bootstrap-phase2.sh` uses the `sensor-tls` secret's presence (checked per-context) as its idempotency gate — skip bundle regeneration if it already exists. `roxctl` is intentionally not used or required.

**The `stackrox` namespace must exist on the target cluster *before* the init-bundle secrets are applied — confirmed live:** `infra/rhacs/secured-cluster.yaml` and `infra/rhacs/secured-cluster-onprem.yaml` both bundle a `Namespace: stackrox` object alongside the `SecuredCluster` CR, but the bundle-generation step runs *before* that file is applied, so on a cluster with no prior RHACS state the namespace doesn't exist yet when `oc apply -f <decoded-bundle>` runs. All three secret creations fail with `namespaces "stackrox" not found`, and if the script only checked exit codes casually it would silently continue — worse, under `set -euo pipefail` (which this script uses) it aborts the whole step outright. The `SecuredCluster` then reports `Irreconcilable: "some init-bundle secrets missing in namespace \"stackrox\""` and never becomes `Available`. Fix: `bootstrap-phase2.sh` explicitly ensures the `stackrox` namespace on cloud (`oc create namespace stackrox --dry-run=client -o yaml | oc apply -f -`) *before* generating/applying the init bundle, independent of the later `SecuredCluster` apply. Onprem's `stackrox` namespace already exists from `central.yaml`, so no separate `oc create namespace` step is needed there.

**Full verification confirms the whole chain works**: `curl -sk -u admin:<password> https://<central-host>/v1/clusters | jq` shows **two** registered clusters — `onprem` and `cloud` — both with `healthStatus.overallHealthStatus: "HEALTHY"` and `sensorHealthStatus: "HEALTHY"` once each cluster's Sensor, Collector, Admission Control, and local Scanner are all Running. If only `cloud` shows up, onprem's `SecuredCluster` was never applied — check `oc get securedcluster onprem -n stackrox --context onprem`.

**Central's admin password is auto-generated — `central-htpasswd` secret, key `password`:**
`Central.spec.central.adminPasswordSecret` is left unset in `infra/rhacs/central.yaml`, so the operator auto-generates a random admin password and stores it in the `central-htpasswd` secret (same namespace as Central) under the `password` key. There is no separate `roxctl`/CLI step to retrieve it — `oc get secret central-htpasswd -n stackrox -o jsonpath='{.data.password}' | base64 -d`.

**Central's Route object is named `central`, not `stackrox-central`:**
Even though the `Central` CR itself is named `stackrox-central` (`infra/rhacs/central.yaml`), `spec.central.exposure.route.enabled: true` creates a Route object named `central` (plus a second `central-mtls` internal route) — confirmed live (`oc get route -n stackrox`). Scripts must query `oc get route central -n stackrox`, not `oc get route stackrox-central`.

**Central readiness — poll condition `Available`, not `Deployed`:**
Unlike the Skupper `NetworkObserver` CRD (whose only "done" signal is `Deployed`), the RHACS operator's `Central`/`SecuredCluster` CRDs report `Deployed: True` as soon as the underlying Helm release is installed — long before Central is actually up (confirmed live: `Deployed` went `True` at nearly the same instant the CR was created, while `central`/`central-db`/`scanner` pods were still `0/1 Running`/`Pending`). The correct "actually serving" signal is the `Available` condition, which only flips `True` once all workloads report ready (message: `"N of M workloads are not ready: ..."` while waiting). Both `bootstrap-phase2.sh`'s wait loop and its checkpoint check poll `Available`.

**Sensor↔Central traffic: cloud goes over Central's public Route, onprem stays in-cluster:**
Cloud's `SecuredCluster.spec.centralEndpoint` is set to Central's Route host (`<host>:443`, no scheme prefix) — Sensor on cloud connects directly to Central's public gRPC-over-HTTPS endpoint (reencrypt-terminated Route), authenticated via the init-bundle-issued mTLS certs. This does **not** use the Skupper/RHSI tunnel; no new Skupper Connector/Listener is required for RHACS. Onprem's `SecuredCluster` (self-monitoring) instead sets `centralEndpoint: central.stackrox.svc.cluster.local:443` — the in-cluster Service — since Sensor and Central are co-located on the same cluster; there's no reason to hairpin through the external Route for same-cluster traffic.

**Central's default resource requests can exceed available capacity on constrained sandbox clusters:**
On a cluster already running the full banking-demo stack plus RHACM/GitOps/other operators, `central-db`'s default resource request can fail to schedule (`FailedScheduling: Insufficient cpu`), leaving Central permanently non-`Available` even though the CR/Route/secrets are all correctly created. This is a capacity-planning issue, not an automation bug — if `central-db` stays `Pending`, check `oc describe pod -n stackrox -l app=central-db` for `FailedScheduling` before assuming the RHACS wiring itself is broken; either free up worker capacity or reduce `spec.central.resources`/`spec.scanner` sizing.

echo "user: admin"
echo "password: $(oc --context onprem get secret central-htpasswd -n stackrox -o jsonpath='{.data.password}' | base64 -d)"

Local basic-auth login only (username `admin`) — `infra/rhacs/central.yaml` does not configure OpenShift OAuth as an auth provider, unlike the Network Observer console above.

**PostgreSQL JDBC has no read/connect timeout by default — a connection pool holding stale connections from before an RHSI outage never self-heals without this:**
`account-service`, `ledger-service`, and `transaction-processor` all connect to onprem PostgreSQL via the RHSI-tunneled `postgresql-primary` Skupper Listener (cloud). Confirmed live during link-failure chaos testing: when that Listener gets recreated (its backing K8s Service gets a new identity), any connection Agroal already had pooled through the *old* one goes half-dead — and PostgreSQL JDBC has no socket-level read/connect timeout configured by default, so Agroal's validate-on-borrow check against that dead connection hangs indefinitely instead of failing fast (`account-service`: `"Sorry, acquisition timeout!"`; `ledger-service`: `"An I/O error occurred while sending to the backend"`). The pool never recovers on its own — previously required a manual pod restart. Fix: `quarkus.datasource.jdbc.additional-jdbc-properties.{socketTimeout=10,connectTimeout=5,tcpKeepAlive=true}` (and the same under `quarkus.datasource."read".jdbc.*` where a read datasource exists) on all three services. With this, the validation check fails in seconds, Agroal destroys the dead connection and transparently opens a fresh one within the same acquisition attempt — confirmed live, zero pod restarts needed across a full real break→restore cycle.

## Dashboard Frontend — Full-Height Layout Notes (UI Milestone)

The dashboard is considered feature-complete for its current milestone (Overview, Traffic & Chaos, Autoscale Watch panes) — no new widgets are planned, so remaining UI work is layout polish: making existing panes fill the available viewport instead of leaving dead space above the footer. This surfaced several non-obvious PatternFly/React layout pitfalls, all confirmed live against the real deployed dashboard, worth keeping in mind for any future layout change in `services/dashboard-frontend`.

**`@patternfly/react-charts`' `<Chart>` (Victory-based) requires a hardcoded numeric `height` prop — there is no responsive/percentage height option:**
Width was already made responsive per-chart via a `ResizeObserver` on a `containerRef` div (`TpmChart.tsx`, `ThroughputChart.tsx`, and `AutoscaleWatchPanel.tsx`'s internal `ReplicaChart` each independently reimplemented this same pattern — since consolidated into a shared `src/hooks/useElementSize.ts` hook), but height stayed fixed at 210/195/185px respectively, which is why charts previously occupied a fixed slice of their card regardless of how much vertical space was actually available. Extending the same `ResizeObserver` pattern to also measure height (with a sane floor, e.g. `Math.max(160, measuredHeight)`, so charts don't collapse on the very first layout pass) is the correct fix — but see the feedback-loop note below before doing this again elsewhere.

**Measuring a container to size a `<Chart>` inside it creates a `ResizeObserver` feedback loop unless the chart is taken out of layout flow:** Confirmed live: a `flex:1;min-height:0` measured container does *not* stop an explicitly-sized child (the chart's rendered SVG, given a hard pixel `height` prop) from growing its own parent — a child's explicit size isn't clipped by the parent's flex-basis. That fed the next `ResizeObserver` tick a larger number, compounding each render until a chart settled around **12,000px tall**, forcing the whole pane to scroll instead of filling exactly. Fix: wrap the `<Chart>` (and its "Collecting data…" placeholder) in a `position:absolute;inset:0` div inside the `position:relative` measured container — the standard technique also used internally by libraries like Recharts' `ResponsiveContainer` — so the chart can never influence the size of the box being measured. Add `overflow:hidden` on the measured container too, as a defensive clip during the first paint before the observer's first tick fires.

**PatternFly's `isFilled` `PageSection` (`.pf-v5-c-page__main-section.pf-m-fill`) defaults to `flex-shrink:0` — it grows to fit content but never shrinks back to the viewport:** Confirmed live via computed-style inspection (`flexGrow=1 flexShrink=0`). This means a per-view `height:'100%'`/CSS-grid-`1fr` trick on your own top-level view element only *looks* like it clamps height — it actually only works by coincidence, when that view's natural content already happens to be smaller than the available viewport. The moment a view's content grows past the viewport (e.g. after enlarging cards' fixed padding/fonts), the fill-section just keeps growing and an ancestor (`.pf-v5-c-page__main`) scrolls to compensate — exactly the "pane needs scrolling" symptom this milestone is meant to eliminate. The real, root-cause fix (in `public/index.html`'s global `<style>` block, alongside the existing `.pf-v5-c-page { min-height: 0 !important; }` override using the same pattern): `.pf-v5-c-page__main-section.pf-m-fill { flex-shrink: 1 !important; }`. This lets the section properly clamp to the real available height, with its own `overflow-y:auto` kept as a safety net for content that genuinely can't fit even at minimum size.

**Enlarging *fixed* (non-negotiable) content — padding, margins, font-size on cards/tiles/text blocks — to "fill available space" is fragile and bit us twice in the same session:** Once a card is `flex:1;min-height:0` inside a stretched column, growing its padding/fonts/margins increases its *minimum* required height, but that minimum isn't validated against the *actual* split height until real data renders — a screenshot at one window size can look fine while the card is actually a few dozen pixels too tall for a smaller split (e.g. two `ClusterCard`s sharing a column, or a KPI-tiles-plus-breakdown-card split on Autoscale Watch). Confirmed live twice: `ClusterCard` needed 296px but the flex split only gave it 248.5px (the "Traffic weight" row silently spilled past the card's own border, since nothing clipped it); `ScalerBreakdownCard` needed 482px against an allocated 318.5px (163.5px short) once its sibling KPI tiles were also over-enlarged, forcing a page scroll. **The fix that actually held:** dial fixed padding/margins/font-sizes back close to their original (pre-enlargement) footprint — real visual "growth" should come from genuinely elastic elements only (chart plot area via the hook above, percentage-height bars, `viewBox`-scaled SVG animations) that shrink and grow with whatever space is actually available, never from fixed-pixel text-block chrome. Add `overflow:hidden` on any card using `justify-content:'space-between'` inside a `flex:1` slot as a defensive safety net, so a future mismatch clips silently instead of visually spilling past the card border.

**Verifying a "fills the viewport" claim requires a live computed-style check, not just a screenshot at one window size:** The reliable check, run in the browser console (or via the `mcp__claude-in-chrome__javascript_tool` in an agent session) against the live route:
```js
const main = document.querySelector('.pf-v5-c-page__main');
main.scrollHeight > main.clientHeight  // true means something overflows — investigate before calling it done
```
For a specific card/column suspected of being too tight, compare `el.getBoundingClientRect().height` (what it was actually allocated) against `el.scrollHeight` (what its content needs) — a mismatch there pinpoints the exact offending element instead of guessing from a screenshot.

**`services/dashboard-frontend/build/` must never be committed — it's dead weight, not a deployment artifact:** Unlike a typical CRA repo, this directory *was* tracked in git (pre-existing before this note), despite `services/dashboard-frontend/Dockerfile` being a proper multi-stage build that runs its own `npm install && npm run build` inside the image — the committed `build/` output is never read by anything and just accumulates diff noise on every local `npm run build`. Now covered by `.gitignore` (`services/dashboard-frontend/build/`), mirroring the existing `**/target/` convention for the Java services above.

**Local build check catches the same errors Tekton would, before pushing:** `cd services/dashboard-frontend && CI=true npm run build` — the `CI=true` env var makes Create React App treat ESLint warnings (including unused-import warnings left behind after refactoring, e.g. dropping a manual `useState`/`useRef`/`useEffect` `ResizeObserver` block in favor of the shared hook above) as build failures, matching how a real CI run would behave, instead of silently succeeding with warnings that only surface later in the Tekton build log.
